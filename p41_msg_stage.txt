test(benchmarks): string slash-star regression guard - no source bug (Task 41)

The Task 40-era observation that string literals containing slash-star
appeared to swallow one space (print('[' + 'a /* b' + ']') printing
[a /*b]) does not reproduce. Investigation result: NOT a source bug.

Evidence:
- Byte-level trace via temporary instrumentation (DBGSTR in string(),
  DBGBUF before emitConstant, DBTTAKE in takeString; removed before
  landing): the lexer token arrives intact (raw=['a /* b'], rawLen=8
  including quotes), escape processing preserves every byte (outLen=6,
  buf=[a /* b]), takeString receives len=6.
- All execution paths (script file, -c, stdin pipe), both quote
  styles, and every surviving binary (root rudy.exe from the Task 40
  build window and the fresh Release build) agree: len('/* b') == 4,
  len('a /* b') == 6, '[' + 'a /* b' + ']' == '[a /* b]'.
- The correct counts: '/* b' is / * SPACE b = 4 chars; 'a /* b' is
  a SPACE / * SPACE b = 6 chars. The Task 40 session expectations
  (5 and 7) were character miscounts.
- The one anomalous [a /*b] print is attributed to the corrupted
  incremental build produced by the documented Task 40 build race
  (MSB6003/MSB3491 tlog lock collisions); no surviving binary
  reproduces it.

Changes (no compiler/lexer/runtime source changes):
- benchmarks/repro_t41_string_slashstar.rdy: 16-check regression
  guard pinning exact lengths, content preservation (both quote
  styles, variable roundtrip, concat identity), edge shapes
  (leading/doubled slash-star), escape-built / * SPACE characters,
  and the Task 40 block-comment interplay outside strings.
- CHANGELOG.md: note under Unreleased/Added.
