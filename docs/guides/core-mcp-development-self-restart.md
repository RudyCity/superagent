# SuperAgent Core self-restart through MCP and agents — operator runbook

Updated: 2026-11-04. Applies to supervised API Core, not the interactive
T-Line/CLI process and not existing legacy MCP OAuth owner hot-patching.

## Architecture and supported operations

- The opt-in Core supervisor is a **separate long-lived process** from each
  API worker. It owns the stable local public API listener. It launches a new
  worker with authenticated readiness and atomically updates its generation
  checkpoint. It retains old session-owned workers.
- A separate Core Guardian can recover its own verified supervisor after a
  crash. It will not take over a foreign or unsupervised process.
- Five MCP operations exist: `superagent_core_status` and
  `superagent_core_plan` (safe), `superagent_core_restart`,
  `superagent_core_rollback`, and `superagent_core_drain` (write).
  The agent uses `manage_core` with `status|plan|restart|rollback|drain`.
- MCP requires an authorized OAuth write scope, local YOLO enabled, and
  dangerous-tool exposure for mutations; a gateway never grants additional
  permissions. A human operator's approval cannot be inferred solely from
  an AI-supplied `confirm:true`; operators must enforce their client/UI's
  approval and access policies. No tool may replace an unsupervised Core.
- The development restart is **Core API worker only**. It never restarts
  the interactive CLI/T-Line owner, Cloudflare/OpenAI MCP tunnels, OAuth
  issuer, Muse, Telegram, or subprocesses from the old session.

## Safe development sequence

1. Verify that the target API port is not an existing unsupervised service.
   Start a supervised Core on an unoccupied port:
   `bun src/cli.tsx core start --port 7888`. For compiled installations,
   run `bun run build` then `bun dist/cli.js core start --port 7888`.
2. Confirm `superagent core status --port 7888` responds with an
   authenticated Core owner. Source mode hashes current source contents.
   Compiled mode requires `dist/core-build-identity.json` generated by
   `bun run build`; modified source/compiled content fails closed.
3. Call `superagent_core_plan` with `{"action":"restart","port":7888}`,
   or `manage_core({action:"plan",targetAction:"restart",port:7888})`.
   Inspect `codeChangedSinceActiveWorker`, `supervisorPid`,
   `expectedBuildDigest`, `operationId` and worker PIDs.
   **A plan is not permission to act.** Request explicit approval in the
   remote MCP client as appropriate and confirm write scope.
4. Call `superagent_core_restart` with `port`, `operationId`,
   `expectedBuildDigest`, `confirm:true`. The agent uses
   `manage_core` with those exact parameters and `action:"restart"`.
   The preflight rejects an unexpected build change, an unauthorized
   port, missing supervisor, malformed operation ID or missing consent.
5. Verify `verified=true`, the old worker is retained, the new worker
   has the planned SHA-256 digest, `codeChanged` reflects source changes,
   and the public port/supervisor PID remain stable.
6. If the HTTP response times out or disconnects, **retry the same
   operationId and digest**. Do not generate a second ID blindly.
   A completed operation is returned as `replayed:true`. A pending
   operation is blocked, never silently executed a second time.
7. Use a fresh plan/ID for a rollback or guarded drain; do not drain
   active/pinned sessions. The supervisor caps retained generations at
   four and has a five-second restart cooldown.

## Crash, timeout, and unknown outcomes

- A pending operation survives a supervisor crash in
  `~/.superagent-r/core-control-operations-PORT.json`. The journal
  contains only hashed IDs, action, expected digest and status, not raw
  tokens, prompts or chat data. A new supervisor refuses all mutations
  until the unknown outcome has been reviewed.
- Run `superagent core operations --port 7888` to inspect hashed
  operation receipt metadata without modifying services.
- After at least two minutes, inspect `superagent core status --port 7888`,
  worker ownership, checkpoints, active sessions, and external side
  effects. A local human operator can explicitly mark a pending receipt
  reviewed with `superagent core reconcile-operation --port 7888
  --operation-id ID --observed-pid PID --acknowledge-unknown`. This only
  records a review; it does not replay, stop, kill or recover any process.
  Do not issue a fresh restart until unresolved external tool effects
  have been reconciled independently.
- Full OS reboot cannot promise unattended migration of running LLM
  state, open SSE/WebSocket streams, arbitrary tool side effects or OAuth
  sessions. Existing explicit-resume and durable checkpoint gates remain.

## Existing MCP port 8857: no automatic URL-preserving migration

On the 2026-11-04 read-only audit, the existing MCP 8857 was an
**OAuth Legacy owner** with a Cloudflare Quick Tunnel, while the default
Core 7888 had no supervised owner. A Legacy owner cannot hot-load this
new MCP tool catalog. Restarting/replacing the Legacy Quick Tunnel can
change its random trycloudflare.com hostname, invalidating the connected
ChatGPT MCP URL. **It is impossible to promise that exact random URL
survives an independent Legacy-to-Reloadable migration.**

Run the non-mutating audit:
`bun scripts/audit-core-mcp-dev-readiness.ts --mcp-port 8857 --core-port 7888`.

Safe future path:

1. Leave the existing Legacy process and public URL intact.
2. Prepare an isolated **Reloadable** MCP owner and a separately supervised
   Core on unoccupied staging ports, with isolated config and OAuth clients.
   Verify MCP OAuth read/write scopes, Core restart/replay, and rollback.
3. To maintain a durable externally recognizable URL across future owner
   migrations, provision a **named Cloudflare Tunnel** with an operator-owned
   DNS hostname and credentials. DNS/origin ownership must be verified. Do
   not claim the existing Quick Tunnel URL can be converted in place.
4. With explicit operator-approved cutover, migrate OAuth clients through
   intentional reauthorization, inspect active sessions and tool effects,
   and switch to the named endpoint. Monitor both old and new independently.
5. Do not stop the Legacy endpoint until all clients intentionally migrate
   and operators approve final decommission. No code in this change
   performs, schedules, or authorizes that migration automatically.
