# SuperAgent Tray — Cron & Runtime Manager — Implementation / Decisions
Date: 2026-11-04
Repository: RudyCity/superagent, branch main
Commit/push: **not authorized**; all changes remain in the working tree.

## Goal and architecture

Add a compact Windows-first Tauri v2 **companion tray utility** for existing SuperAgent daemon cronjobs, runtime inspection and reminders. **T-Line is the official SuperAgent desktop application**; this app is named **SuperAgent Tray** (`apps/superagent-tray`) to avoid name and installer identity collisions. This is a management surface, **not an independent cron runner**.

```text
Tauri webview (static HTML/CSS/JS, no secrets / shell / HTTP permission)
    │ specific Tauri IPC action, with limited request fields
    ▼
Tauri Rust backend (local server-info.json, private bearer token)
    │ HTTP only to 127.0.0.1:<recorded Core port>, no redirects
    ▼
SuperAgent Core daemon REST API (existing auth + DaemonScheduler)
    │ owns job state, cron parsing, run ledger, safety rules
    ▼
daemon-jobs.json + daemon run ledger
    │ successful text-only reminder runs
    ▼
Tauri native 15s poll + OS notification + persistent run-ID dedup
```

Tauri code: `apps/superagent-tray/src-tauri`, static UI `apps/superagent-tray/ui`. Existing scheduler extended in `src/core/daemon/daemonScheduler.ts` / `daemonTypes.ts`. Existing REST authorization is not bypassed, changed, or widened.

## Implemented

- Tauri v2 tray: open manager, new reminder, Runtime Detection, quit. Close hides window rather than killing native reminder polling.
- Desktop Cron Manager: list/read, create, edit (name/content/schedule), pause/resume, delete with confirmation, manually run with confirmation, ledger history, scheduler status/start button.
- Schedule presets: one-time (five-field cron + maxRuns=1), daily, weekly, advanced cron; client rejects one-time dates in the past.
- Reminder kind: deterministic text-only, no AI agent/model/tools/skill, no retries or multi-agent mode. Execution appears in the same daemon ledger, preserving audit records and runtime policy. Existing agent/system maintenance jobs remain separate.
- Updated daemon PATCH to permit `maxRuns: null` to convert one-shot to repeating. The persisted field becomes undefined; an invalid positive limit remains rejected.
- Tauri Rust calls only fixed authenticated loopback daemon routes. Auth token read from owner config directory; JavaScript cannot call arbitrary URLs or read token. CLI shell execution is not exposed to webview.
- Native plugin notifications for successful reminder runs, 15-second poll even when window hidden, dedupe with `desktop-notified-runs.json` bounded at 500 run IDs, stale runs older than two hours ignored.
- Included tray icons for Windows/macOS and Tauri config. Tauri build can be run from desktop folder.
- **Runtime Detection:** separate read-only native inventory and UI in `apps/superagent-tray/src-tauri/src/runtime_detection.rs` and `apps/superagent-tray/ui/runtime.js`. Read-only Core projection in `src/core/runtime/desktopServiceProjection.ts`, exposed at authenticated `GET /api/desktop/runtime-services`. Auto-refresh every 20 seconds; tray menu opens this panel.
  - Multiple Core registrations are discovered using bounded `server-info*.json` records. Only an authenticated `/api/status` with valid JSON establishes Core online; OS PID is checked independently.
  - CLI, MCP and agent processes are derived from the official process journal with OS birth-time and fresh heartbeat checks; stale entries are not claimed to be running.
  - Per-Core scheduler, gateway, Muse Watch, Telegram, MCP and Cloudflare status is presented as **Core-local** evidence, not inferred global liveness. Cloudflare is only active when tunnel process evidence exists, not merely a WebSocket listener.
  - T-Line transport default port 7891 and registered channel-hosts are checked against their read-only identity/health endpoints and OS PIDs; a transport with unavailable Core backend is degraded.
  - Operator can switch the cron manager's selected Core to a registered **authenticated** online loopback server. No arbitrary host, raw port scan, command execution, bearer exposure, or automatic process start.
  - Separate Delegate WS listeners and custom T-Line ports without registered metadata remain unverified rather than labeled active.
- **Independent MCP/tunnel/Muse remote service detection remediation (2026-11-04):** `apps/superagent-tray/src-tauri/src/remote_service_detection.rs` scans bounded per-port `mcp-*.json` and `tunnel-*.json` registry records. MCP uses owner process birth validation plus a credential-free 401 Bearer challenge from its `/mcp` listener (state `observed`, rather than declaring authenticated client connectivity). Cloudflare verifies cloudflared process executable and a fresh successful healthy heartbeat (state `online`), otherwise `observed/unverified/stale`. No URLs or tokens leave native code.
  - `src/core/remoteAgent/museWatcher.ts` now publishes a bounded, token-free `muse-watch-<pid>-<nonce>.json` heartbeat every 10s, and removes it on stop; Rust requires verified PID birth and freshness under 30s and distinguishes ready transport from listener-only. Existing watcher processes must be restarted to load this new code; **do not restart live Muse tasks automatically**.
  - `apps/superagent-tray/ui/runtime.js`, `ui/index.html` add an independent-services section. Core-scoped MCP/Muse/tunnel labels are explicitly named `Core-local` to prevent false `Inactive` statements for independent hosts.
  - No destructive registry cleanup, no bearer transmission to the webview, no unsolicited probe of the public tunnel origin, and no *automatic* stop/start/replay. Explicit owner-authenticated manual lifecycle actions are described below.
- **User-confirmed lifecycle controls (2026-11-04):** `apps/superagent-tray/src-tauri/src/runtime_control.rs` adds strictly allowlisted `service_action(kind,action,port,pid)`, never generic termination/HTTP/exec. It authenticates to registered private owners and verifies PID/identity again at action time. Managed MCP `stop` checks zero active sessions/in-flight requests, drains then stops gracefully **without force**; `restart` uses reloadable MCP backend and verifies preserved public URL. A registered Core Supervisor offers generation-preserving `restart`; **Core Stop, bare Core restart and standalone Cloudflare restart are deliberately unsupported**.
  - `src/core/remoteAgent/museOwnerLifecycle.ts` gives independently hosted Muse Watch a private loopback owner endpoint and separate protected `muse-owner-<pid>-<nonce>.json` token record (not in the public heartbeat). Tray checks live PID/birth, fresh heartbeat and owner identity before `/_muse/stop` or `/_muse/restart`. An explicit Stop holds an idle owner for a later Restart, while normal CLI stop tears it down. Active/queued tasks, public tunnel rotation and unverified owners fail closed. No started batch is replayed.
  - `src/core/runtime/desktopMuseLifecycle.ts` and authenticated fixed-shape `POST /api/desktop/muse-lifecycle` implement the equivalent for Core-local Muse Watch with exact PID validation, lifecycle lock and same-watcher option/callback preservation. Endpoint is unavailable until Core reloads the updated code.
  - `apps/superagent-tray/ui/runtime.js` shows confirmation dialogs and disabled Stop/Restart buttons when permission/safety evidence is absent. It only invokes native allowlisted actions using the discovered port/PID, with result feedback and a subsequent rescan. Users must intentionally authorize each operation.
  - **Unchanged:** Cloudflare directly, Channel Hosts, T-Line Transport, Core without Supervisor. No forced process kills, no automatic owner migration, no public tunnel URL changes.
- **New connection creation from Tray (2026-11-04):** `apps/superagent-tray/ui/index.html` and `ui/runtime.js` add an explicit New Connection wizard with four fixed types: external MCP client (HTTPS/loopback HTTP, OAuth option); safe OAuth MCP tunnel (Cloudflare/OpenAI ID, separate managed owner); Core HTTPS tunnel on exactly the selected authenticated port; and Muse WSS Cloudflare tunnel with isolated per-port token/configuration. `apps/superagent-tray/src-tauri/src/main.rs` checks input names, URL, fixed kinds, provider/port and selected Core before its allowlisted `create_connection` command forwards to the **authenticated loopback** `POST /api/desktop/create-connection` route. The route rejects Origin, forwarded headers and non-loopback requests. `src/core/runtime/trayConnectionCreation.ts` delegates to existing SuperAgent managers and serializes startup, disallowing duplicate owner takeovers.
  - Existing MCP names cannot be overwritten, HTTPS URL credentials/query secrets are rejected. MCP tunnel creates only **safe/read-only OAuth tools**, no `allow-dangerous`; startup is verified by the existing managed owner. Core tunnel enforces same selected port; no arbitrary upstreams. Muse rejects active remote tasks, conflicting watcher/tunnel ports, and uses `skipRemoteTaskAbort` to prevent forced cancellation even if a task starts between checks. It never overwrites Telegram credentials.
  - The MCP one-time OAuth bootstrap and Muse WSS bearer prompt are copied by Core into the local OS clipboard via the existing trusted helper; they are never returned to the WebView. Results display the endpoint only and report whether setup copying succeeded. On failure, documented local CLI/config recovery applies. User confirmation precedes creation.
  - The running Core must load the new route through an operator-controlled restart; the application does not restart Core or start any real public tunnel during tests. The external MCP client is saved/configured but **not claimed connected** until session MCP initialization.
  - Tests: `tests/trayConnectionCreation.test.ts` verifies validation, locked startup, real isolated model-config persistence and rejection of duplicates; `tests/desktopRuntimeUi.test.ts` verifies confirmation and four distinct UI invocations; Rust native unit tests ensure no arbitrary fields, ports, local Core impersonation or shell commands pass.
- **Regenerate Token (2026-11-04):** Runtime Detection cards now present **Regenerate Token** only for verifiable safe owner contracts. Native `regenerate_token` accepts only kind + bound port/PID and rechecks authenticated identities. For managed, reloadable **Cloudflare MCP OAuth**, the authenticated local Core route `POST /api/desktop/regenerate-token` calls existing `regenerateManagedMcpBootstrapCode`, rotating the **one-time approval code only** (public URL, OAuth access/refresh grants, Core bearer and cloudflared identity remain unchanged). The new private setup is copied directly to the OS clipboard. Existing OpenAI tunnel ID/static-Bearer and legacy MCP owner rotations are explicitly unsupported.
  - For Muse WebSocket, the independent Muse owner exposes authenticated private `/_muse/token/rotate`, and Core-local Muse uses the same fixed Core route. Actual owner invokes existing `MuseWsServerTransport.rotateToken` with five-minute previous-token grace and pushes `token_refresh` to the authenticated active Muse session. Active/queued tasks and Telegram/HTTPS watcher modes are rejected. `src/core/runtime/desktopTokenRegeneration.ts` verifies MCP managed owner PID and exact input shape; `src/core/remoteAgent/museOwnerLifecycle.ts` serializes token rotation with stop/restart. No token/code is serialized to the WebView, inventory API or error logs; clipboard exit status is checked instead of assumed.
  - Test coverage includes isolated one-time code validation/copying, no-secret responses, stale owner PID rejection, private Muse HTTP 401/409/200 lifecycle, explicit user confirmation, and native owner verification. **No user-owned live token was regenerated during these tests**. Existing Core and older independent Muse owners must load new code through an operator-controlled restart; Tray deployment itself never rotates credentials.
- **Runtime detection tests:** Rust unit tests for registration identity, HTTP authentication, stale/reused PID protection, channel-host matching, degraded T-Line, MCP Bearer challenge, fresh/stale Muse heartbeat, authenticated mock MCP reload/Core Supervisor restart/Muse Stop, and token omission; TypeScript tests for redacted Core-local service projection, confirmation UI, and actual isolated Muse owner stop/restart over HTTP.
- **Automatic tray startup (2026-11-04):** `src/core/runtime/trayAutoLauncher.ts` locates a verified per-user or project-built `superagent-tray.exe` and requests `--background` launch without blocking long-lived process startup. Entrypoints: `src/cliMain.tsx` (interactive CLI), `src/server.ts` (successful REST bind), `src/core/runtime/coreSupervisor.ts` (successful public supervisor bind), `src/cli.tsx` (independent channel-host, transport, MCP server). On Windows `tauri-plugin-single-instance` prevents duplicate tray owners and notification pollers; manually reopening the binary can focus an existing manager while background triggers do not steal focus.
- **Tray Settings UI + native persistence (2026-11-04):** `apps/superagent-tray/ui/settings.js` and a fourth `Tray Settings` page / tray context-menu item control seven strictly validated preferences: auto-launch with long-lived SuperAgent, close-window-to-tray, native reminder notifications, reminder poll interval, runtime scan interval, schedules/history refresh interval and startup page. Rust `src-tauri/src/tray_settings.rs` persists only a bounded, versioned `tray-settings.json` file with an atomic create-new/rename write; malformed/extra fields and symlinked files are refused. It never writes Core/daemon/MCP or Muse configuration. Disabling notifications silently acknowledges completed reminders without showing Windows toasts; the independent native poll loop rereads settings at each cycle. The runtime and jobs browser timer loops are reconfigured on settings save without duplicates or Core restart.
  - `src/core/runtime/trayAutoLauncher.ts` checks persisted auto-launch preference **before** spawning, with `SUPERAGENT_TRAY_AUTOSTART=0/1` retaining explicit operator override precedence; malformed files fail closed. Manual launch still works. Close window either hides to tray (default) or exits only the Tray utility; it never stops Core, MCP, tunnels or Muse.
  - UI `Save Settings` waits for native acknowledgment and does not claim success if persistence fails. `Restore Defaults` previews until Save. `--diagnose-settings` prints safe preferences for read-only smoke verification without opening a GUI. Startup page respects an explicitly requested window hash. No Windows login startup task/registry entry is installed.
  - Tests: Rust settings roundtrip/replacement, malformed/oversize file and strict settings schema; `tests/desktopTraySettingsUi.test.ts` validates bound controls, save/reject/reset, startup page and immutable input schema; `tests/trayAutoLauncher.test.ts` checks stored opt-out, environment override and malformed config handling.
- **Custom frameless native title bar (2026-11-04):** `apps/superagent-tray/src-tauri/tauri.conf.json` disables Windows decorations but retains native resize/maximize/minimize. `ui/titlebar.js`, `ui/index.html`, `ui/styles.css` provide a branded 44px strip with accessible **Minimize**, **Maximize/Restore**, and **Close** controls plus mouse drag and title-bar double-click-to-toggle maximize. Drag starts only after an intentional 5px primary-mouse movement and does not fire for controls or a maximized window. The native allowlisted `tray_window_action` targets only Tauri's `main` window; permitted actions are `minimize`, `toggle-maximize`, `start-drag`, `close`, and read-only `state`. The native Close event continues to honor saved `closeToTray` (hide vs. quit Tray only), never affecting Core/MCP/Muse processes. The WebView receives **no generic window management capability**. `tests/desktopTitlebarUi.test.ts` exercises the layout, drag threshold, double-click, buttons, state icons and accessibility. Native build and post-install single-instance checks are required.
- **Per-user installation:** `scripts/install-superagent-tray.ts` explicitly copies the compiled PE to `~/.superagent-r/bin/superagent-tray.exe`. This is used by globally installed SuperAgent packages even if they don't contain `apps/` build outputs. Paths/CLI guards are covered in `tests/trayAutoLauncher.test.ts`. A live Windows smoke verified one persistent PID across repeated launch attempts. Only one user-facing tray starts; Core processes remain independently owned.
- **Controls and boundaries:** `SUPERAGENT_TRAY_AUTOSTART=0` disables this feature. No GUI starts in tests, private Core workers, or identified headless CI. Tray never starts/stops AI processes automatically, never replays a task batch, and persists after the launching CLI exits. Logon startup and non-Windows autolaunch remain separate product decisions.

## Existing system and constraints

- Core uses one `DaemonScheduler` in memory and persists `~/.superagent-r/daemon-jobs.json`. Independent scheduler processes operating concurrently can overwrite state; Tauri **never** edits this file directly.
- Core REST endpoints `/api/daemon/status`, `/api/daemon/start`, `/api/daemon/jobs`, `/api/daemon/jobs/run`, `/api/daemon/runs` already exist. Tauri only allows these fixed actions.
- The frontend does not start Core itself. Core must be running and the daemon scheduler must be started by the operator; otherwise desktop clearly reports disconnected or stopped.
- Native Windows notifications require an installed app and notification permission/support; `cargo check` alone does not establish toast delivery.
- Cron is minute-resolution and interpreted by Core in **system-local time**; DST/ambiguous hours are not independently handled by Tauri.
- The dashboard reuses existing Core data; no second desktop database of jobs, no new agent grants.

## Rudy decisions required

1. **Placement:** keep a separate `superagent-tray` Tauri tray app vs integrate tray UI into existing T-Line native desktop project (outside this repository).
2. **Lifecycle:** tray auto-launch on SuperAgent process startup is implemented. Still open: start **SuperAgent Core itself** automatically on sign-in and manage one daemon owner via supervisor, or require manual Core startup? Core autostart could have security/CPU/billing implications.
3. **Notification channels:** OS only vs also Telegram/Discord/Slack for reminders; any default for `notifyGateway`; user consent for external delivery.
4. **Time semantics:** system local zone only vs explicit per-job IANA timezone/DST/recovery policies; missed reminders after sleep/offline (two-hour catchup window in this version); once-only semantics when a scheduled minute is missed.
5. **Security:** Windows installer signing, per-user encrypted token storage/ACL verification, multi-profile/project isolation. A **native single-instance policy is now implemented** for this tray app.
6. **Agent jobs:** should the desktop surface allow new agent jobs at all, or restrict creation to safe reminders and offer agent jobs view-only? In this prototype, agent creation is explicit with workspace and existing Core headless safety policy.
7. **Runtime operations:** should desktop remember a selected Core across restarts, discover nondefault T-Line ports via a new owner-verified registry, and add opt-in offline/online notifications? Current selection is process-local; runtime scans are read-only and never restart processes.
8. **Delegate detection:** provide a future authenticated read-only Delegate bridge status endpoint (without exposing pairing secrets) before claiming extension connectivity in the desktop UI.
